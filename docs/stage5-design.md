# 段階5（JIT-to-wasm）の設計案

作成: 2026-09-29（段階5 の開始時）。**§1〜§4・§9 はユーザー確認済み（2026-09-29）**。
5-1 は実装済み（結果は計画書 §9 段階5）。実装で変えた点: JIT の枠は CodePage の中ではなく
CodeCache の別の表に置いた（JIT なしの wasm の速度を保つため）。計画書 §3.2・§6.2・§8・§9 段階5
の「判断が必要」に答えるもの。確認が取れたら決定事項を計画書に移す。

## 0. 試作で確かめたこと（tmp/proto-jit、非コミット、依存の追加なし）

wasm-bindgen 0.2.129 の `inline_js` と `wasm_bindgen::memory()` / `function_table()` だけで、
Node 24（`--target nodejs`）で次が動いた:

- JS で組み立てた wasm のバイト列を `new WebAssembly.Module` → `Instance` し、
  **本体（Rust）の線形メモリを import** させると、生成コードが Rust の構造体
  （static の中身）を直接書き換えられる。
- 呼び出しの費用（2,000 万回、最良値）: Rust の関数ポインタ経由 4.2ns・
  **本体の関数テーブルに登録して Rust から call_indirect 4.0ns**・
  **JS の中継（inline_js）経由 12.9ns**。
- 小さなモジュールの compile＋instantiate は 1 個あたり約 10µs（1,000 個で 10ms）。
- 本体の関数テーブルは既定では伸ばせない（lld が max=min にする）。テーブル方式には
  リンカの `--growable-table` が要る（依存ではなくビルド設定）。

参考: 今のインタプリタ（Node の wasm）は約 70M 命令/秒 = 1 命令 14ns、動的なブロック長の
平均は 4.9 命令（計画書 段階4）なので、1 ブロック約 70ns。JS の中継の 13ns は無視できない。

## 1. wasm のバイナリを作る方法 → 自作の小さなエンコーダ（推奨）

- 使う範囲は小さい: セクション（type・import・function・export・code）、LEB128、
  i32/i64 の整数命令・load/store・制御（block/loop/if/br/br_if/br_table）・local。
  400 行程度の見込み。コアの「依存なし」を保てる。
- wasm-encoder（Bytecode Alliance）は正確で保守されているが、コアに初めての依存が入る
  （生成はプラットフォーム非依存なのでコアに置きたい）。
- 検証: 生成したモジュールは Node の `WebAssembly.validate` と差分テスト（§8）で確かめる。
- 解釈の再確認（計画書 §8 の約束）: 汎用のコード生成ライブラリ・wasm の仕様書は
  「既存エミュレータのコード」に当たらない。JIT の設計（ブロックの切り方・出口・
  命令数の数え方など）は既存エミュレータ（JIT を持つもの）を参照せず、ARM ARM と
  **WebAssembly Core Specification（W3C）** を一次資料として自分で決める。

## 2. 生成したモジュールの読み込みと呼び出し

置き場所:

- **コア**（`rust/core/src/jit/`、std のみ）: ブロックの切り出し（IR から）、wasm の
  バイト列の生成、ブロックの表・実行回数・無効化の管理、生成コードとの取り決め
  （`JitCtx`）。ネイティブでもビルドされ、単体テストはネイティブで回る
  （生成コードの実行だけは wasm のホストが要る）。
- **web**: `JitHost` トレイト（コアが定義）の実装。バイト列 → モジュールの
  instantiate、関数の呼び出し、モジュールの解放。machine は `Option<Box<dyn JitHost>>`
  で持つ（呼ぶのはブロックに入るときだけなので dyn でよい）。ネイティブの CLI は
  持たない（= インタプリタのみ）。

呼び出しの方法（段階を分ける）:

- **5-1: JS の中継**（`inline_js` の `jit_call(id, ctx)`。依存なし・unsafe なし）。
  生成モジュールは本体の memory だけを import する。
- **5-2 以降: 関数テーブル**。生成関数を本体のテーブルに登録し、Rust から
  テーブルの添字を関数ポインタとして呼ぶ（`unsafe` の transmute が 1 か所。
  `--growable-table` を足す）。CLAUDE.md の規則どおり、実際のブロック連結の後に
  計測で効果を確かめてから入れる（試作では 1 回 9ns の差）。
- js-sys・web-sys は要らない（`wasm_bindgen::memory()`/`function_table()` と
  `inline_js` で足りる）。
- `new WebAssembly.Module`（同期）は Chrome のメインスレッドでは 4KB までだが、
  エミュレータは Worker で動く（§3.4）ので問題ない。

## 3. 状態の置き場所（生成コードが直接読み書きするもの）

- 生成関数の形は `(ctx: i32) -> i32`。ctx は `#[repr(C)] struct JitCtx` の線形メモリ上の
  アドレスで、Rust が呼ぶ直前に埋める:
  - 入力: `regs`（`Cpu::regs` の先頭）・`cpsr` のアドレス、ソフト TLB の先頭、
    RAM のアリーナの先頭、MMU の `perm_r`/`perm_w`/`pid` の値、残りの命令数
    （`budget - n` を u32 に切り詰めたもの）
  - 出力: 実行した命令数、出口の理由（PC は regs[15] に書く）
- それ以外の構造体（`Cpu`・`TlbEntry`）は repr(C) にせず、生成時に
  `std::mem::offset_of!`・`size_of` でオフセットを埋め込む（配置は Rust に任せたまま、
  生成コードとずれない）。
- アドレスは wasm32 でだけ意味がある（ネイティブではホストがないので使わない）。
- unsafe の扱い: 5-1 の JS の中継では Rust 側に unsafe は出ないが、「呼び出しの間、
  生成コードが cpu・TLB・アリーナを書き換える」ことは Rust から見えない。呼び出しの
  前に `&mut` から作ったアドレスだけを渡し、呼び出し中は参照を使わない、という規則を
  呼び出し箇所に SAFETY 相当のコメントで書く。安全の担保は差分テスト（§8）。

## 4. 生成コードからコアへの呼び出し → 最初は作らない（出口で戻る）

生成コードは **コアの関数を一切呼ばない**。扱えないことが起きたら、その命令の
**手前で** 関数から戻り（サイド出口）、インタプリタがその命令から続ける。

- 出口にする場合: ソフト TLB のミス・権限なし、ロード先が RAM でない（MMIO）、
  ストア先の `wram` が NO_RAM（コードページ = 書き込み検出が要る）、非アライン
  （MMU の fast path と同じ条件）、ブロックに入る時点で残りの命令数がブロック長より
  少ない。
- こうすると、MMIO・TLB の埋め方・フォルト・CP15・例外・割り込みはすべて今の
  インタプリタの経路で処理され、生成コードはそれらと同じ規則を再実装しない。
  TLB も変えない（ヒットのときだけ読む）ので、ソフト TLB の状態は 1 命令ずつの
  場合と一致する。
- 戻った後: `n += 実行した命令数`。次の 1 命令は必ずインタプリタ（run_page）で
  実行する（出口の命令で JIT に入り直して空回りしないため）。
- 割り込み線・上限・Thumb・code_cur_va の規則: JIT するブロックには、割り込み線や
  期限を動かす命令（MMIO・MSR・CPSR を書く命令・MCR）が入らない（出口になるか、
  ブロックの対象外）。したがって、ブロックに入る前に Rust が確かめた
  「割り込みなし・ARM 状態・code_cur_va が有効・上限の残り」は、ブロックの間ずっと
  成り立つ。生成コードの中で割り込み線を見る必要はない。
- MMIO の関数呼び出し（出口ではなくその場で呼ぶ）は、出口の頻度を計測してから
  必要なら 5-3 以降で検討する（呼んだ後に割り込み線・期限・上限を確かめる規則が要る）。

## 5. 単位と発火条件

- **ブロック** = 1 つの物理ページ内で、入口の PC から最初の「PC を書く命令・対象外の
  命令・ページ末尾」まで。1 IR 命令 = 1 ARM 命令なので、ブロックの長さ = 命令数。
- 実行回数: デコードキャッシュのページに、命令ごとの u32 の枠（未コンパイルなら
  回数、コンパイル済みならブロックの番号）を持つ。1 ページ 4KB で、デコード済み
  約 2,000 ページなら約 8MB（デコード表 16MB の半分）。
- 数える場所: `run_page` を「JIT あり」と「JIT なし」の 2 つに単態化する
  （`run` の入口で 1 回だけ分岐）。**JIT なしの経路は今と同じコード**なので、無効時の
  速度は変わらない。JIT ありの経路では、ブロックの先頭（直前の命令が PC を書いた、
  またはページに入った）で枠を見る。
- 閾値に達したブロックを待ち行列に積み、ある数（案: 32 個）たまるか run の区切りで
  まとめて 1 モジュールにする（instantiate の回数を減らす）。閾値と個数は計測して
  決める（初期案: 閾値 64 回）。
- 無効化: コードページへの書き込み（MMU の code_invalidated）でデコード表を捨てる
  ときに、そのページの枠も捨てる。変換の変化（世代）は今の code_cur_va の仕組みで
  JIT への入口が塞がる（JIT に入るのは cur_instr が有効なときだけ）。全ブロックが
  捨てられたモジュールは JS 側の参照を外して GC に任せる。
- 上限: 生成したコードの合計（バイト数・モジュール数）に上限を設け、超えたら全部
  捨てて作り直す（まずは単純に。iOS Safari のメモリ予算を計測してから値を決める）。
- すべて派生情報で、スナップショットには含めない（読み込み・リセットで捨てる）。
  JIT の有無・コンパイルの時期はゲストの状態に影響しない（生成コードが
  インタプリタと完全一致するので）。

## 6. 命令数の正確さ

- ブロックの入口で「残り ≥ ブロック長」を確かめ、足りなければ 0 命令で戻って
  インタプリタが 1 命令ずつ進める（ブロックは平均 5 命令と短いので損は小さい）。
  ブロックの途中では命令を数えない（出口のときだけ「何命令目で出たか」を返す）。
- 条件不成立の命令も 1 命令と数える（インタプリタと同じ）。
- 期限（デバイスイベント）は machine が上限に入れて渡しているので、上限を守れば
  期限も守られる。ブロックの途中で上限が下がることはない（MMIO をしないため）。
- アボートは出口でインタプリタに任せるので、正確な PC・命令数で例外になる。
- 5-2 でブロックを連結（ループを wasm の中で回す）しても、各ブロックの入口で同じ
  確認をする。

## 7. 使う wasm の機能

- **MVP ＋ 符号拡張命令（i32.extend8_s/16_s）だけ**。符号拡張は Safari 14.1・
  Chrome 74・Firefox 62 から。末尾呼び出し・例外処理・SIMD・スレッド・
  multi-memory は使わない（Safari/iOS の古い版を切らないため。出口は戻り値で表す）。
- 64 ビットの命令数は Rust 側で持ち、生成コードは 32 ビットの残り数だけを扱う。
- 対応確認: 生成コードの有無は実行時に選べる（`WebAssembly` が使えない・生成に
  失敗したらインタプリタに戻る）。

## 8. 検証の方法

- **差分テスト（Node）**: web クレートに試験用の API（`jitDiffTest(seed, n)` 等）を置き、
  ランダムな状態・ランダムな命令列（対象の Op を全部含む。特化の差分テストと同じく
  全 Op を試したかを確かめる）を、JIT（閾値 1 = すぐコンパイル）とインタプリタで
  実行して、CPU 状態・RAM・TLB・実行命令数を突き合わせる。MMU 有効（ページテーブル・
  権限・FCSE・MMIO のページ・コードページ）の場合も含める。Node のスクリプトを
  `tools/check.sh` に足す（wasm32-wasip1 のテストは JS のホストがないので JIT を
  試せない）。
- **基準シナリオ**: `GOLDEN_RUNNER=wasm` に JIT を有効にする指定（例:
  `CERULEAN_JIT=1`、閾値も指定可）を足し、全シナリオの完全一致を確かめる。
  閾値 1 でも通す（コンパイル時期に依存しないことの確認）。
- **食い違いの調査**: run-wasm.mjs に trace-hash を足し、ネイティブの
  `--trace-hash N` と突き合わせる。

## 9. 段階の分け方（案）

- **5-1 最小の JIT**: エンコーダ、ブロックの切り出し、特化済みの単純な Op
  （データ処理の即値・レジスタ・即値シフト、LDR/STR/LDRB/STRB の即値、B/BL/BX/MOV pc）
  の生成、サイド出口、JS の中継での呼び出し、実行回数と無効化、切り替え、差分テスト、
  基準シナリオの一致。速度は「ブロックごとに Rust に戻る」ので大きくは上がらない
  見込み（仕組みの正しさを固める段階）。
- **5-2 ブロックの連結**: 同じモジュール・同じページ内の直接分岐を wasm の中で回す
  （loop＋br_table）。関数テーブルでの呼び出し（計測して効果があれば）。
- **5-3 対象の拡大**: LDM/STM・ハーフワード・ライトバック・条件実行の多いブロック、
  ページをまたぐ連結（世代の確認つき）、必要なら MMIO をその場で呼ぶ。
- **5-4 メモリ予算と捨て方**、各ブラウザ・iOS Safari での計測。

各段階で Node の wasm の基準シナリオの完全一致（JIT あり・なし）と計測を行い、
計画書・CLAUDE.md・README を更新してコミットする。
