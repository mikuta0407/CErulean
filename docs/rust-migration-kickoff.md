# Rust 移行の開始用プロンプト

新しいセッションの最初に、以下をそのまま貼り付けて使う。

---

CErulean（WM5 LLE エミュレータ）の Rust 移行を始めたい。
計画は docs/rust-migration-plan.md にある（2026-09 にユーザーと合意した内容）。
設計方針と確認済みの事実は CLAUDE.md、現状は README を参照。
まず計画書を最後まで読み、Go 版のコード（特に snapshot・mmu・cpu/arm・
machine/smdk2410・emu）を必要なだけ読んでから始めること。

## 前提（計画書の要約。詳細は計画書が正）
- エミュレータのコアを Go から Rust に全面移行する。最初の出荷先はブラウザ
  （wasm。PC の Chrome/Firefox/Safari と iOS/iPadOS の Safari）。
- 将来は JIT-to-wasm（ブラウザ）・ネイティブ JIT（Android/PC/iOS-JIT）・
  インタプリタ（App Store 版 iOS）を揃える。今回は範囲外だが、構成は妨げないこと。
- 今の Go 実装は、Rust 版が完全一致するまで **正解の基準** として残す。
  移行中は Go 版も Rust 版も機能を凍結する（不具合の修正だけ両方に入れる）。
- 一致の定義: 同じスナップショット・同じ入力スクリプトから、同じ命令数で
  スナップショットの **展開後のバイト列**・UART 出力・画面の **RGBA 画素列**・
  レジスタが一致すること（圧縮後のファイルや PNG は実装ごとに違うので比べない）。

## 今回のゴール: 段階0（準備）を完了し、段階1 の最初の設計判断の案を出す
1. 計画書 §12 の未決事項のうち、段階0 に必要なものを最初にまとめて質問する
   （リポジトリ構成、依存の初期セット、ツールの導入、Rust のコメントの方針、CI）。
   ツール（rustup の wasm32-unknown-unknown ターゲット、wasm-bindgen-cli、Node.js
   など）で入っていないものがあれば、導入を依頼すること。
2. Go 側の道具を作る（計画書 §5.2）:
   - snapdump（チャンクごとの名前・版数・位置・長さ・SHA-256、2 つの比較）
   - trace-hash（N 命令ごとに、RAM 以外のチャンクの展開後バイト列の SHA-256）
   - 途中でハッシュを取っても最終状態が変わらないことのテスト
3. 基準シナリオを作る（計画書 §5.1）:
   - Today のスナップショットを固定の -rtc で作る手順を決める
   - rec-5taps を、Today 起点の再現可能なスクリプトとして作り直す
   - 期待値（チャンクごとのハッシュ・UART・画面・レジスタ）と、作り直す手順
     （スクリプト）を testdata/golden/ にコミットする。イメージ・スナップショット
     自体はコミットしない
   - Go のテストに埋め込まれた合成プログラムを testdata の命令語ファイルに
     切り出し、Go と Rust の両方から使えるようにする
4. tmp/ にある調査・比較の道具（tmp/tools の segspeed・ihist・genrate、
   tmp/m5ref の verify.sh・bench.sh・cmp.sh）をリポジトリの道具として整理する。
5. Rust のワークスペースの骨組み（rust/ に core・cli・web）を作り、ネイティブと
   wasm の両方でビルドとテストが通ることを確認する。rust-toolchain.toml と
   Cargo.lock で版を固定する。
   比較スクリプトは標準エラーの文言ではなく、命令数・レジスタ・停止の種類などの
   構造化された値を比べる形にする（計画書 §5.2）。
6. CLAUDE.md に Rust 移行中の規則を追記する（コメントの方針、unsafe の扱い、
   ゲストの演算は wrapping・シフト量の場合分け、64 ビットの値に usize を使わない
   （wasm32 では 32 ビット）、依存の承認、一致確認の手順）。
7. 段階1 の最初の判断「Rust の所有権に合わせた設計の置き換え」（計画書 §3.3）の
   案を、比較（性能・書きやすさ・Go との対応の取りやすさ）付きで出して確認を取る。
   必要なら小さな試作をしてよい。

## 進め方（これまでと同じ）
- 止まるたびに「何が原因で、何を実装するか」を短く報告すること
- 大きな設計判断（計画書で「判断が必要」としたもの、依存の追加）は実装前に案を示して
  確認を取ること
- 仕様が不確かな箇所は推測で埋めず、TODO コメントと質問として残すこと
- 仕様の根拠は ARM ARM (DDI 0100) と S3C2410X User's Manual（tmp/docs/）と Go 版の
  コード・コメント。既存エミュレータのコードは参照しない
- 各機能にテストを書き、区切りのいいところで論理単位のコミットをすること
- CLAUDE.md・README・計画書（docs/rust-migration-plan.md）を随時更新すること
  （計画と違う判断をしたら計画書にも理由を残す）

## 手元の環境（2026-09 時点）
- イメージ: tmp/images/PPC_USA.bin（基準に使う）、PPC_JPN.bin ほか（非コミット）
- Today のスナップショット: tmp/snap/today.snap（作成時の -rtc が不明なので、
  基準用には段階0 で作り直す）
- マイルストーン5 の比較用の出力: tmp/m5ref/（非コミット）
- /tmp は tmpfs で容量が小さいので、大きな出力はプロジェクトの tmp/ に置くこと
