# CErulean Rust 移行計画（ブラウザ版を第一目標とする）

作成: 2026-09-28（マイルストーン5 完了時点）。ユーザーとの相談の結論:

- エミュレータのコアを **Go から Rust に全面移行**する。
- 最初の出荷先は **ブラウザ**（PC の Chrome/Firefox/Safari、iOS/iPadOS の Safari・WebKit）。
- 将来は実行方式を 3 つ揃える:
  - **JIT-to-wasm**: ブラウザ・WebKit
  - **ネイティブ JIT**: Android、Windows/Linux/macOS、StikDebug 等でデバッガ接続して JIT を許可した iOS
  - **インタプリタ**: App Store 版の iOS ネイティブ、全方式の正解の基準
- 今の Go 実装は、Rust 版がネイティブで同じ動作になるまで（段階1 の完了まで）
  **動作の正解の基準（オラクル）** として使う。
- **Go 版とのファイル形式・CLI の互換は要件にしない**（2026-09-28 見直し）。
  スナップショット・入力スクリプト・CLI のフラグと出力は Rust 側で自由に設計してよい。
  Go 版と比べるのは「ゲストから見た動作」（命令数・レジスタ・RAM・UART・画面）だけで、
  比較は形式に依存しない値で行う（§5）。段階1 の完了後は基準を Rust 版の出力に
  切り替え、Go 版は比較に使わない（§9「Go 版の扱い」）。

この文書は計画であり、実装の詳細な仕様は Go のコードとコメント、CLAUDE.md の
「確認済みの事実」が一次情報になる。段階1 の間は、動作が食い違ったら Go のコードが
正しい（移行中に Go 側の不具合が見つかった場合は、先に Go を直して基準を更新する）。

## 1. 目的と成功の基準

### 目的

1. 1 つの Rust コードから、ブラウザ（wasm）と将来のネイティブ（iOS/Android/PC）の
   両方に出せるコアを作る。
2. 重い区間（アプリ起動など）の実行速度を上げる。最終的には JIT で実時間に近づける。
3. ブラウザで「イメージを読み込む → 起動 or スナップショットから再開 → 操作 →
   自動保存 → タブが kill されても再開できる」体験を作る。

### 各フェーズ共通の成功の基準（変えてはいけないもの）

- **決定論性**: 同じスナップショットと同じ入力スクリプトからは、どの実装・どの
  実行方式（インタプリタ／JIT）・どのプラットフォームでも、同じ命令数で同じ状態に
  なる。段階1 ではこれを **Go 版とのゲストから見た動作の完全一致** で確かめ、
  以降は Rust のインタプリタ（ネイティブ）を基準にする（§5）。
- スナップショットから再開した結果は、通しで実行した結果と完全に一致する
  （Go 版と同じ性質。Rust 版の中で確かめる）。
- **Rust 版が一度公開したスナップショット形式は読めなくしない**（ブラウザの利用者の
  保存データを失わないため。形式を変えるときは版数を上げ、旧版の読み込みを残す。§4.3）。
  Go 版のスナップショットは読めなくてよい。
- 仕様の根拠は一次資料のみ（ARM ARM DDI 0100、S3C2410X User's Manual Rev 1.1、
  WinCE 5.0 の文書、実イメージの実測）。**既存エミュレータのコードは参照しない**
  （JIT の設計も含む）。汎用のライブラリ（圧縮・wasm 生成・コード生成器など）は、
  エミュレータではないので使ってよいが、依存を足すたびにユーザーの承認を取る（§8）。

### 非目標（この計画ではやらない）

- 新しいハードウェア機能（音・電源ボタン・UART 受信・PXA27x 構成など）。
  **段階1 の完了まで、Go 版と Rust 版のコアの動作を凍結**し、移行を先に終える。
  例外は不具合の修正で、両方に入れて基準を作り直す。
  - 凍結するのは **ゲストから見える動作**（命令の意味、デバイスのレジスタ値と
    割り込みの時刻、入力がゲストに届く時刻と値）。スナップショットやスクリプトの
    形式、CLI、フロントエンド、状態を変えない最適化は、Rust 側で自由に進めてよい。
  - 段階1 の完了後は、Go 版は凍結したまま（直さない）。Rust 版はコアの動作を変えて
    よいが、変えたら基準（testdata/golden）を作り直し、理由をコミットに残す。
    ハードウェアの新機能自体は、移行（段階5 まで）の後に回す。
  - 対応イメージは今のところ QVGA 版（PPC_USA.bin・PPC_JPN.bin）。VGA 版は画面
    サイズ・タッチの変換式（QVGA の touch.dll から得た固定式）が未検証なので対象外。
- ネイティブアプリ（iOS/Android/PC）のフロントエンドとネイティブ JIT の実装。
  ただし §3 の構成は、これらを後から足せる形にしておく（§10）。

## 2. 現状の棚卸し（移植の対象）

Go 実装: 約 14,800 行（テスト込み）。パッケージと移植先の対応:

| Go パッケージ | 役割 | 行数(概算・テスト除く) | Rust の置き場所（案） |
|---|---|---|---|
| `snapshot` | 保存形式（CERUSNAP＋flate、チャンク） | 380 | `cerulean_core::snapshot` |
| `loader` | B000FF(BIN) / .nb0 のローダー | 190 | `cerulean_core::loader` |
| `bus` | 物理アドレス空間、RAM/MMIO、監視、Probe32、RAMPage | 390 | `cerulean_core::bus` |
| `mmu` | ARMv4 MMU/CP15、ソフト TLB、フェッチ猶予、コードページの印、世代 | 920 | `cerulean_core::mmu` |
| `cpu` | CPU の境界 interface | 90 | `cerulean_core::cpu`（trait） |
| `cpu/arm` | ARMv4T インタプリタ、デコードキャッシュ、ブロック実行、特化、アイドル検出、逆アセンブラ | 2,900 | `cerulean_core::arm` |
| `device/s3c2410` | INTC・PWM タイマー・LCD・RTC・ADC/TS・SPI・UART・DMA スタブ・値保持スタブ | 1,350 | `cerulean_core::s3c2410` |
| `machine`, `machine/smdk2410` | ボード構成、実行ループ（RunUntil・時間同期・アイドルスキップ）、入力、キーボード用マイコン、スナップショットの並び | 1,050 | `cerulean_core::machine`, `cerulean_core::smdk2410` |
| `script` | 入力スクリプトの解釈と書き出し | 350 | `cerulean_core::script` |
| `emu` | イベントの照合・対話入力の記録 | 220 | `cerulean_core::emu` |
| `cmd/cerulean` | CLI（info/run/serve）、トレース、監視、PNG、HTTP フロントエンド | 1,200 | `cli`（ネイティブ）と `web`（ブラウザ） |

移植で落としてはいけない「設計上の要点」（それぞれ Go の該当ファイルのコメントに
理由がある。Rust でも同じ理由コメントを残す）:

- 命令のデコードと実行の分離（decode.go / exec_*）。デコードキャッシュ・特化・
  将来の IR/JIT の前提。
- `cpu` 境界は trait。**ただしホットパスは静的ディスパッチ**（ジェネリクスか具象型）
  にする（§6.1）。
- S3C2410 固有の知識は s3c2410 と smdk2410 だけが持つ。machine は差し替え可能。
- 未実装命令は黙って NOP にせず、`UndefinedError{PC, Word, …}` で止める。
  アーキテクチャ上の未定義命令（`Arch=true`）はゲストに例外として配送する。
- 未マップの物理アドレスへのアクセスは `BusError`（エミュレーション停止）、
  MMU のフォルトは `AbortError`（ゲストに例外として配送）。
- 仮想時間は命令数から決まる（1 命令 = 3/8 PCLK、InstructionsPerSecond=135.2M）。
  壁時計を見るのはフロントエンドだけ。
- CLAUDE.md の「確認済みの事実」（OEMAddressTable、DE の準仮想デバイス、LCD・
  タッチ・キーボードの観察結果、MMU 有効化直後のフェッチ猶予など）。

## 3. 目標の構成

### 3.1 リポジトリ構成

Go 版はリポジトリ直下のまま（モジュールパスを変えない）。Rust は `rust/` に
Cargo ワークスペースを置く。

```
CErulean/
  (Go のコード: 段階1 の完了まで動作の正解の基準。その後は凍結・退役)
  rust/
    Cargo.toml              ワークスペース
    core/                   エミュレータのコア（パッケージ名 cerulean-core。std のみ、プラットフォーム非依存）
    cli/                    ネイティブの開発用 CLI（run/info、トレース、監視、PNG、比較ツール）
    web/                    wasm のエントリ（Worker 用 API。wasm-bindgen）
    web/www/                ブラウザのフロントエンド（HTML/JS/CSS。ビルド不要の素の JS を想定）
  testdata/golden/          一致確認の基準（スクリプト・期待ハッシュ。イメージ由来の実データは置かない）
  docs/
```

- クレート名を `core` にしない。Rust の組み込みクレート `core`（`core::mem` など）と
  名前がぶつかり、依存側の `core::…` が曖昧になるため。ディレクトリは `rust/core`、
  パッケージ名は `cerulean-core`（コード中は `cerulean_core`）とする。
- **コアは 1 クレート**（`cerulean-core`）にまとめ、Go のパッケージはモジュールで再現する。
  Rust はクレートをまたぐと LTO なしではインライン化されにくく、ホットパスが
  cpu・mmu・bus をまたぐため。境界は `pub(crate)` と trait で守る。
  依存方向は Go と同じ（cpu/arm → cpu の trait、mmu → bus、machine が組み立てる）。
- コアはファイル・時計・スレッドに触れない（Go の「コアは純 Go・OS 非依存」の
  置き換え）。入出力は呼び出し側から `Read`/`Write` やコールバックで渡す。

### 3.2 実行方式の差し替え点

```
                ┌───────────── cerulean_core::machine（RunUntil・時間同期・アイドルスキップ・入力・スナップショット）
                │
Core::run(budget) ─┬─ インタプリタ（デコードキャッシュ＋特化。段階4 で IR ベースに）
                   ├─ JIT-to-wasm（段階5。ブラウザ）
                   └─ ネイティブ JIT（将来。Android/PC/iOS-JIT）
```

- 実行方式が違っても、machine から見た契約は Go の `Core.Run` と同じにする:
  「最大 budget 命令を実行し、実行した命令数を返す。途中で Executed() が読め、
  LimitRun で上限を下げられ、スピン検出で打ち切る」。
- 状態（レジスタ・CPSR・バンク・MMU・TLB）は実行方式に関係なく同じ構造体に
  持つ。JIT のコードもその構造体（wasm では線形メモリ上）を読み書きする。
  スナップショットは常に同じ内容になる。

### 3.3 Rust の所有権に合わせた設計の置き換え（段階1 の最初に決める）

Go 版は、デバイスどうし・MMU と CPU がクロージャで互いを参照している
（タイマー → INTC の Raise、INTC → CPU の SetIRQ、ADC・SPI・キーボード → INTC、
時間を持つデバイスの MMIO ラッパ → machine の syncTime、MMU → CPU の世代フック・
コード書き換えの通知）。Rust の所有権ではこの形をそのまま書けない
（`Rc<RefCell<…>>` にするとホットパスで実行時の借用検査が入る）。案:

- **machine がすべてを具象型のフィールドとして所有**し、バスの MMIO の振り分けは
  「領域 → デバイス番号」の表と `match` による静的な分岐にする。
- デバイス間の通知はコールバックではなく、**戻り値や小さなイベントの記録**
  （例: 「割り込み要求のビット」「期限が変わった」）にし、machine がアクセスの後に
  まとめて処理する。発生した命令境界は Go と同じにする。
- CPU が MMU を（ジェネリクスで）所有する形なら、世代やコード書き換えの通知は
  フックではなく **CPU が MMU のフィールドを直接見る** 形にできる。
- 時間の同期（ブロック途中の MMIO での catchUp）は、CPU の実行ループから
  machine の関数を呼ぶ経路が要る。CPU の Run を machine 側のループに組み込むか、
  CPU にバス（＝machine のデバイス群）への可変参照を渡す形にする。

どれも「観測できる動作は Go と同じ」が条件。**判断が必要**（段階1 の最初に案を
比較して決める。性能と書きやすさの両面で小さな試作をしてよい）。

エラーは Go の「AbortError（ゲストに配送）／BusError・UndefinedError（停止）」の
区別を、Rust の enum（`Result<_, MemError>` 等）で表す。

**決定（2026-09-28 ユーザー確認）: 案 A「CPU の状態とシステムを並べて持つ」**。

- machine が `cpu`（レジスタ・バンク・PSR だけのデータ）と `sys`（MMU・ボードの
  デバイス・時間・デコードキャッシュ・実行の上限）を別々のフィールドとして所有し、
  `arm::run(&mut cpu, &mut sys, budget)` が両方を借りる。`sys` は trait（CPU から
  見たシステム）を実装し、`arm::run` はそのジェネリクスで静的ディスパッチになる。
- Go のコールバックはすべて `sys` の中の直接の呼び出しにする: デバイス → INTC は
  戻り値（満了したチャネルのビット等）をボードが INTC に渡す、INTC → CPU は
  割り込み線のフィールド（CPU が命令境界で読む）、MMIO → 時間の同期 → LimitRun は
  `sys` の中の実行の上限（Go の runN/runBudget）を直接下げる。
- デコードキャッシュは `sys` 側に置く（MMU がコードページへの書き込みを見つけたら
  その場で無効化できる）。実行中ページの有効性は CPU が MMU の値を直接見る
  （Go の SetGenHook の代わり）。
- 比較（試作、tmp/proto-own。小さな命令セットで同じ規則のブロック実行・時間同期・
  割り込み・コードの無効化を実装し、結果の完全一致を確認）: 案 A 243〜255M 命令/秒、
  Go の形を `Rc<RefCell>` で移す案 B 166〜181M 命令/秒。案 B は CPU の実行中に
  デバイスが共有状態を借りると実行時に panic する危険もある。イベントの列にためる
  案 C は、効果の時点がずれて Go との一致の論証が要るので採らない。
- **保存する状態と派生情報の分け方（CheckFields の代わり）**: 各部品を「保存する
  状態の構造体」と「作り直せる派生情報」に分ける。保存・読み込みでは保存する状態の
  構造体を `..` なしで全フィールド分解し、フィールドを足して保存を忘れると
  コンパイルエラーになるようにする。派生情報は読み込み後に作り直す。

### 3.4 ブラウザでの配置

- エミュレータ（wasm）は **Dedicated Web Worker** で動かす。メインスレッドは UI
  （canvas 描画・入力・操作パネル）だけ。
- Worker ⇄ メインの通信は `postMessage`。画面は変化したときだけ RGBA の
  ArrayBuffer を transfer で送る。**SharedArrayBuffer は使わない**（使うには
  COOP/COEP ヘッダでのクロスオリジン分離が必要で、配信先によっては設定できない
  ため。性能上どうしても必要になったら再検討）。
- 実時間との同期は Worker 側（serve の loop と同じ規則: 仮想時間の小さな単位で
  進め、進みすぎたら待ち、遅れすぎたら追いつくのを諦める）。Worker は処理を返さないと
  メッセージを受け取れないので、1 単位ごとに制御を返す（setTimeout／MessageChannel。
  タイマーの最小間隔の制約は段階2 で実測する）。

## 4. Go 版と動作を一致させるために再現が必要な細部

段階1 では Rust 版のゲストから見た動作を Go 版と完全に一致させる（§5）。形式
（スナップショットのバイト列・スクリプトの書式・CLI）は合わせなくてよいが、
次の細部はゲストの動作や命令数に現れるので、同じ選択をしないと一致しない。

### 4.1 ゲストの動作に現れる実装の選択（漏れやすいもの）

- **ソフト TLB**（mmu/tlb.go）: 1024 エントリの直接マップ、添字は MVA[21:12]、
  キャッシュしない変換（細テーブル・tiny ページ、AP が一様でない小ページ、フォルト、
  ドメインフォルト）、MMU 無効時も恒等変換を TLB に載せること、全無効化の契機
  （c1/c2/c3/c8 の書き込み。c13 では無効化しない）、ミス時にだけ埋める規則。
  ゲストがページテーブルを書き換えて TLB を無効化しなかった場合、古い変換が
  使われるかどうかがこの規則で決まるので、**埋める・捨てるタイミングまで一致させる**
  （実機の ARM920T の TLB とは構造が違うが、Go 版と一致させるのが段階1 の条件）。
  - デコードキャッシュ・ブロック実行・アイドルスキップは「TLB の状態を 1 命令ずつの
    場合と同じに保つ」ように作ってある（CodePage は TLB ヒット時だけ使う、
    watched のエントリの詰め替えで世代を上げる 等。mmu/code.go のコメント）。
    Rust でも同じ規則を守る。
  - TLB の中身はスナップショットに含める（再開後も通し実行と同じになるように）。
- **フェッチ猶予**（mmu/mmu.go）: c1 の M ビット変化後、連続する最大 2 命令を旧状態で
  フェッチ。猶予の途中の状態（fetchGrace/graceNext/prevCtrl）もスナップショットに含める。
- **値保持スタブ**（device/s3c2410/stub.go）: 8/16 ビットの書き込みはワード内に合成
  する。読み出し時に OR するビット（forced）がある。
- **ボードの構成**（smdk2410.New）: 各領域のアドレス・大きさ、値保持スタブの初期値
  （CLKPWR のリセット値、WTCON、GSTATUS1 など）、IIS の常時 ready ビット（forced）、
  オープンバス（読み 0・書き無視）の範囲、DE の準仮想デバイスの領域。ゲストから
  読める値なので、そのまま移す。バスの部分デコード（ミラー）機能は今の構成では
  使っていないが、テストごと移す。
- **時間**: 1 命令 = 3/8 PCLK（1/8 ティックの端数を持ち越す）。デバイスの時間を
  まとめて進めても、1 命令ずつ進めた場合と同じ命令境界で割り込みが上がること。
- **タイマー**: 残り時間を PCLK ティックで持つ。周期は (TCNTB+1)×スケール。
  マニュアルアップデート後の最初の満了は TCNTB カウント後。
- **ADC**: 変換時間 = ADCDLY + 5×(PRSCVL+1)（AUTO_PST は 2 回分）。UD_SEN（bit8）の
  扱い、割り込み待ちに入った時点のレベル判定。
- **キーボード用マイコン**: 送信待ちバイト列の扱い（kbd.go）、データ無し時の応答値。
- **CPU**: 非アラインの LDR の回転、LDM でのアボート時のベース復元、STR/STM で PC を
  格納するときの値（PC+8）、UNPREDICTABLE の扱い（Go のコードの選択に合わせる）。
  割り込みを受け付ける命令境界（ブロック実行・アイドルスキップ中も含む）。
- **RTC**（rtc.go）: 基準時刻は「UTC として扱う壁時計の値」で持ち、読み出し時に
  基準 + ⌊経過ティック ÷ pclkHz⌋ 秒 から年月日・曜日（1=日曜）を計算する。
  夏時間は関係しない。Rust の標準ライブラリには暦の計算がないので、グレゴリオ暦の
  変換を自前で書く（またはクレートを承認を得て使う）。
  BCD レジスタへの書き込み（RTCEN=1 の間だけ）で基準時刻を作り直す経路も同じ規則で
  移す。このとき Go の `time.Date` は範囲外の値（2 月 31 日、不正な BCD から来る
  60 秒以上など）を繰り上げて正規化するので、その正規化も再現する。秒未満の
  ティック端数は保つ。曜日の書き込みは捨てる。
  フロントエンドが最初の時刻を与えるときは、ホストの **ローカル時刻の年月日時分秒**
  をそのまま渡す（Go の SetRTC と同じ）。
- **タッチ座標 → ADC の生値**（smdk2410/input.go の touchToRaw）: 整数演算の丸めまで
  同じにする（ゲストが読む値なので）。
- **キーのスキャンコード**（kbd.go）: キー名 → スキャンコードの対応はゲストに届く値
  なのでそのまま移す（キー名の綴りは Rust で決めてよいが、基準シナリオのスクリプトを
  そのまま使うため、当面は Go と同じ綴りにする）。
- **入力の適用時刻**（emu.go）: イベントは「Steps() がその命令数に達した時点
  （次の命令の実行前）」に適用する。`Run(until)` は until ちょうどのイベントを
  適用せずに戻る。同じ命令数のイベントは記述順。対話入力は Inject した時点の
  命令数を刻んで記録する。
- **画面の変換**（lcd.go）: LCD レジスタの解釈と RGB565 → RGBA の変換（HWSWP・
  BSWP・FRM565、ビット拡張の方法）。画面の比較は RGBA の画素列で行うので、変換の
  細部まで一致させる。
- **デバッグ機能と高速化**: -watch（物理アドレスの監視）中は高速経路（ソフト TLB の
  RAM 直アクセス、デコードキャッシュのページ判定・アイドルスキップ・RAMRun）を
  使わない。監視の表示が 1 命令ずつの場合と同じになるようにするため。-trace 中は
  アイドルスキップを止める。命令履歴はスキップ区間をループの PC 列で補う。
- **map の反復順**: 状態を持つ集合（値保持スタブ等）は BTreeMap にするか、反復する
  ときにソートする（Rust の HashMap は反復順が不定。保存結果やゲストの動作が
  実行ごとに変わるのを防ぐ）。

### 4.2 数値の規則

- ゲストの演算は 32 ビットの折り返し（Rust では `wrapping_*` を明示。デバッグ
  ビルドのオーバーフロー検査で落ちないように）。シフト量 32 以上の扱いは Go の
  shiftImm/shiftReg に合わせる（Rust の `<<` はシフト量 ≥ 32 でデバッグビルドでは
  panic、リリースでは結果が変わるので、必ず場合分けする）。
- **wasm32 では `usize` が 32 ビット**。命令数（u64）・ティック・時刻など 32 ビットを
  超え得る値に `usize` を使うと、ネイティブと wasm で結果が変わる。ゲストの値と
  カウンタは必ず明示の幅（u32/u64/i64）で持ち、`usize` は配列の添字だけに使う。
- バイト列の読み書きは `to_le_bytes`/`from_le_bytes` で明示する（ホストの
  エンディアンに依存しない）。
- 浮動小数はコアの状態・時刻計算に使わない（Go 版も使っていない。表示用の
  実時間比などフロントエンドの計算だけ）。スクリプトの時刻（s/ms の小数）も
  10 進のまま整数演算で命令数に換算する。

### 4.3 Rust 版のスナップショット形式

Go 版の形式（CERUSNAP＋flate、チャンク本体の長さが末尾のトレーラ）とは合わせない。
Rust で新しく決める。要件:

- **ネイティブの CLI とブラウザで同じ形式**（ブラウザで保存したものを CLI で開いて
  調べられる。不具合報告にも使う）。記録のスクリプトも同じ。
- 形式の版数とコンポーネントごとの版数を持ち、未知・非対応は必ずエラー（Go 版と
  同じ考え方）。**段階3 で公開した後は、旧版の読み込みを残す**。
- 保存対象の状態はすべて含める（通し実行との完全一致のため）。派生情報
  （デコードキャッシュ、watched、wram、世代、履歴、実行ループの作業領域）は含めない。
  時間の溜めは保存前に必ずデバイスへ同期する。
- 同じ状態からは同じバイト列（圧縮前）になる（Rust 版の中での回帰テストに使う）。
- **ツールで分割しやすい形**にする: 各チャンクの前に名前・版数・長さを置く
  （Go 版は長さを末尾に置いていたため、スキーマを知らないと分割できなかった）。
  snapdump（チャンクの一覧・ハッシュ・2 つの比較）を Rust の CLI に用意する。
- 圧縮方式は自由に選べる（deflate に限らない）。自動保存の頻度を上げたいので、
  段階2 の計測（128MB の RAM の圧縮・展開と OPFS への書き込みの時間）を見て決める。
  コアは圧縮を持たず、無圧縮のストリームを出して、圧縮は CLI とブラウザ
  （CompressionStream 等）の側でする案もある（コアの依存がなくなる）。
- ヘッダにイメージ ID（イメージファイル全体の SHA-256、16 進小文字）を入れ、
  再開時の取り違えの照合に使う。**再開にはイメージ本体は要らない**（イメージは
  RAM に展開済みでスナップショットに含まれる）。
- 読み込みは壊れたファイル・細工されたファイルでも **panic せずにエラーを返す**
  （ブラウザでは panic で wasm のインスタンスが使えなくなるため）。長さの上限
  （Go の maxAlloc 相当）を設ける。スナップショットの読み込みにファジングの
  テストを用意する。
- 差分スナップショット（§7.3）を入れる場合も、展開後の状態は完全な保存と同じになる
  ことをテストで確かめる。

## 5. 一致確認（移行の安全網）

### 5.1 一致の定義と比較する値

Go 版と Rust 版で内部の状態の持ち方・保存形式が違ってよいので、比較は
**ゲストから見える状態**を、形式に依存しない決まったバイト列にして行う。

- **CPU 状態のダンプ**（段階0 でバイト列の並びを `testdata/golden/README` に定義する）:
  命令数（u64）、r0〜r15、全モードのバンクレジスタ（usr/fiq r8〜r14、irq・svc・abt・
  und の r13/r14）、CPSR、各モードの SPSR、CP15（c1・c2・c3・c5・c6・c13）。
  すべて LE の u32/u64。
- **RAM のハッシュ**: SDRAM 128MB 全体の SHA-256。
- **UART1 の送信バイト列**の SHA-256（カーネルのデバッグ出力）。
- **画面**: LCD の変換後の RGBA 画素列（240×320×4 バイト）の SHA-256。
  PNG は圧縮結果が実装ごとに違うので比べない。
- **停止の種類**: max-steps／スクリプトの quit／未実装命令（PC・命令語）／BusError
  （アドレス）。標準エラーの文言は比べない。

デバイスの内部状態（タイマーの残り時間など）は直接は比べない。食い違えば割り込みの
時刻が変わり、CPU 状態か RAM に現れるので、そこから -trace で遡って原因を探す。

### 5.2 基準シナリオ

Go 版で作った次のシナリオを「基準」として固定する。スクリプトと期待値（§5.1 の値。
シナリオの終わりと途中の数点）を `testdata/golden/` にコミットする。
**イメージやスナップショット自体はコミットしない**（Microsoft の再配布物で、容量も
大きい）。実データが必要なテストは環境変数（`CERULEAN_IMAGE` 等）があるときだけ
走らせる。期待値のハッシュはイメージから導いた値だが、元のデータを復元できないので
コミットしてよい。

| 名前 | 内容 | 主に確かめるもの |
|---|---|---|
| boot-1200M | リセットから 12 億命令 | CPU・MMU 有効化・フェッチ猶予・周辺機器の初期化 |
| boot-today | リセットから 36 億命令（Today 完成） | 長時間の一致、アイドル区間 |
| today-calendar | boot-today の続きで Start → Calendar → 右キー | タッチ・キー・アプリ起動 |
| taps-5 | boot-today の続きでタップ 5 回（Start → アプリ起動など。ADC 待ちを含む） | 記録→再生、ADC 待ちのスキップ |
| synthetic-* | 合成プログラム（Go の run_test.go のアイドル・ADC ポーリング等） | イメージなしで CI でも走る一致確認 |

- **どのシナリオも「イメージ＋固定の RTC 初期値＋スクリプト」だけで定義する**
  （起点はリセット。スナップショットの形式が両実装で違うので、スナップショットを
  起点にしない）。スクリプトの時刻は絶対命令数（`@<n>i`）だけを使い、s/ms の換算や
  CLI の細かな規則に依存しないようにする。
- 実行時間を短くするため、各実装は自分の形式で Today のスナップショットを作って
  キャッシュしてよい（通し実行と一致することは各実装の中で保証されている）。
- マイルストーン5 で使った rec-5taps（tmp/serve/rec-044977960000.snap 起点）は、
  対話セッションの途中の状態でリセットから再現できないので使わない。taps-5 で
  置き換える。
- 合成プログラム（synthetic-*）は今は Go のテストコードの中に命令語として書かれて
  いる。両実装で同じものを使えるよう、段階0 で testdata に命令語のファイル（と期待値）
  として切り出し、Go のテストもそれを読む形にする（テストの整理であり、機能の変更
  ではない）。
- 段階1 の完了後は、期待値を Rust 版（ネイティブのインタプリタ）で作り直せるように
  する。以後の段階（wasm・IR・JIT）は Rust のネイティブのインタプリタと比べる。

### 5.3 道具

段階0 で Go 側に作る（Go の既存の CLI への調査用の追加で、コアの動作は変えない）:

- **結果の出力**: 停止時に §5.1 の値（CPU 状態のダンプ・RAM・UART・画面のハッシュ・
  停止の種類）を JSON で書き出すオプション。比較スクリプトはこれを読む。
- **trace-hash**: N 命令ごとに「命令数と CPU 状態のダンプの SHA-256」を 1 行ずつ出す。
  RAM のハッシュは重いので別の間隔で任意に含める。両実装の出力を突き合わせ、
  最初に食い違った区間を見つけ、N を小さくして絞り込み、最後は `-trace` で比べる。
  - ハッシュを取る命令数ちょうどで止まる必要がある（アイドルスキップ・ブロック
    実行が飛び越さないよう、実行ループの期限に入れる）。止まる点を増やしても
    最終結果が変わらないことをテストで確かめる。

Rust 側は同じ値を出す機能を CLI に持つ（フラグ名・書式は Rust で決めてよい。
比較スクリプトが両方の出力を読めればよい）。

- `-trace` の比較は **PC と命令語（と命令数）** で行う。逆アセンブルの文字列は
  比較の対象にしない。
- 食い違いの調べ方の手順: ① trace-hash で命令数を二分探索（CPU 状態で見つからなければ
  RAM のハッシュも入れる）→ ② そこからの -trace（ディスアセンブル付き）を両方で
  比べる → ③ 割り込みの時刻の違いなら、-watch でデバイスのレジスタへのアクセスを
  比べる。

### 5.4 テストの移植

- Go のユニットテスト（テーブル駆動のフラグ計算・シフタキャリー・MMU・デバイス・
  スクリプトなど）は Rust に移す。テストの入力と期待値はそのまま使う（仕様の根拠が
  同じため）。形式に関するテスト（スナップショットのバイト列など）は Rust の形式に
  合わせて書き直す。
- 特化命令と汎用命令のランダム差分テスト（special_test.go）は、Rust では
  「Rust のインタプリタ内の特化 vs 汎用」に加えて、段階5 では「JIT vs インタプリタ」
  に広げる。
- Go の CheckFields（状態フィールドの分類漏れ検出）に相当するものを Rust でも作る。
  構造体のフィールド一覧を得る仕組みが Go と違うので、手段を検討する
  （例: 保存対象と派生情報を別の構造体に分け、保存対象の構造体は SaveState で
  全フィールドを書いたかをテストで確かめる）。
- スナップショットの往復テスト: 保存 → 読み込み → 続きを実行した結果が、通しで
  実行した結果と一致すること（基準シナリオの途中の数点で）。

## 6. 性能の方針

### 6.1 Rust での実装方針

- ホットパス（命令の実行、メモリアクセス、TLB）は **静的ディスパッチ**。
  CPU は具象のメモリ型（MMU）に対してジェネリクスで書き、trait object（`dyn`）は
  境界（machine とフロントエンドの間など）だけにする。
- ビルド設定: release（opt-level=3、LTO、codegen-units=1、wasm は panic=abort）。
  デバッグビルドはオーバーフロー検査が入るので、ゲストの演算は必ず wrapping で書く
  （§4.2）。計測は必ず release で行う。
- 命令の実行関数は関数ポインタの表（Go の `execFn` と同じ考え方）。デコード済み
  命令は小さく保つ（例: ハンドラ番号＋取り出し済みフィールドで 8〜16 バイト）。
- `unsafe` は原則使わない。使う場合は理由と安全性の根拠をコメントに書き、
  テストで守る（例: 境界チェックの除去は計測で効果が確認できたときだけ）。
- Go で入れた高速化はすべて移す（同じ正しさの論拠で）:
  アイドルスキップ（RAM と StableReader の MMIO）、デバイス時間のまとめ進め、
  ブロック実行、デコードキャッシュ（書き込み保護方式・世代・watched）、頻出命令の
  特化、LDM/STM の RAMRun。
- Go で効果がなかったもの（データ用ページキャッシュ、PGO 相当）は、Rust で
  計測し直してから判断する（言語が変わると結論も変わり得る）。

### 6.2 wasm 固有の注意

- wasm32 の線形メモリは最大 4GB。ゲスト RAM（128MB）＋デコードキャッシュ＋
  スナップショットの作業領域を合わせた **メモリ予算** を決める。特に iOS Safari は
  メモリを使いすぎたタブを落とすので重要。
  - Go 版のデコードキャッシュはデコードしたページごとに約 16KB（1024 命令 ×
    16 バイト）で、上限がない。Rust では命令を小さくし、ページ数に上限（LRU 等）を
    設ける。実際に何ページ使うかは段階1 で計測する。上限でページを捨てるときも
    観測できる動作を変えないこと（MMU のコードページの印・実行中ページ・仮想ページの
    対応表との整合を取る。捨てたページは次に実行したときにデコードし直すだけ）。
  - スナップショットの読み書きは、128MB を一度に組み立てずストリームで行う
    （Go と同じ）。
- 線形メモリは縮められず、途中の grow は失敗し得る（特に iOS）。ゲスト RAM は
  起動時に確保し、成長の上限を決めておく。
- wasm と JS の境界をまたぐ呼び出しは重い。1 回の呼び出しで仮想時間の
  まとまった単位（例 10ms）を進める。
- ブラウザごとの wasm 性能差（Chrome/Firefox/Safari）を段階2 で計測する。
- `wasm32-unknown-unknown` の std は一部が使えない: `std::time::Instant`・
  `SystemTime` は呼ぶと panic、スレッド・ファイルもない。コアはもともとこれらに
  触れない（§3.1）が、計測や時刻の取得は web クレートで JS（`performance.now()`・
  `Date`）から取る。CLI 用のコードをコアに混ぜないこと。
- wasm の panic は trap になり、**そのインスタンスは以後使えない**（状態が途中で
  壊れている可能性がある）。Worker は trap（`WebAssembly.RuntimeError`）を捕まえたら
  インスタンスを捨てて作り直す。panic の文言は `std::panic::set_hook` で JS に渡して
  表示する（不具合報告用）。panic 後は命令履歴などを wasm から読めないので、止まった
  理由の表示は文言だけになる。未実装命令・BusError は panic ではなく `Result` で
  返すので、こちらは状態を読める（§7.1）。

### 6.3 計測

- Go の調査用ツール（tmp/tools の segspeed・ihist・genrate 相当: 区間ごとの実時間比、
  実行命令の種類の分布、MMU の世代の頻度）は Rust の CLI のサブコマンドにする。
- 基準の計測: ① リセットから 4 億命令（実処理の区間の命令/秒）、② taps-5 の
  操作区間の再生時間と、タップ直後の区間の実時間比（Go の tmp/tools/segspeed 相当）。
- ネイティブ（Rust の CLI）と wasm（Node、および各ブラウザ）で測る。
- この環境の計測は ±4% 程度ばらつく。比較は交互に 3 回以上走らせて最良値で行う
  （Go の tmp/m5ref/bench.sh 相当を Rust 側にも用意する）。
- 参考値（Go、2026-09、この開発機のネイティブ）: 実処理の区間 75〜80M 命令/秒、
  Today 完成まで 46〜49 秒、rec-5taps（マイルストーン5 の記録）の再生 2.0 秒。
- taps-5（段階0 で測定、Go、2026-09-28）: Today（36 億命令）のスナップショットから
  最後まで（11.5 仮想秒）の再生が 2.1〜2.4 秒。仮想 0.5 秒ごとの区間で、タップ直後は
  実時間の 0.78〜3.3 倍（実処理の割合 12〜59%、実処理の区間 52〜72M 命令/秒）、
  それ以外は 25〜100 倍（アイドル）。リセットからの通し（51.5 億命令）は約 50 秒。

## 7. ブラウザ版の設計

### 7.1 画面構成と操作

- serve の UI をもとにする（画面・一時停止・速度・スナップショット・記録）。
  入力の対応表（PC のキー → キー名、F1〜F5 → App1〜5）と、表示座標 → 240×320 の
  変換は serve の app.js をそのまま移す。
- **タッチ端末（iPhone/iPad）向け**: 物理キーボードがないので、画面外に
  ハードウェアボタン（方向キー・決定・App1〜5・ソフトキー相当）を置く。WM5 の
  文字入力は画面上のソフトキーボード（SIP）をタップすればよい。
- 画面の拡大縮小（devicePixelRatio を考慮した整数倍・`image-rendering: pixelated`）、
  縦横の向きの変化への対応。
- **初回起動の体験**: イメージからの起動は Today まで 36 億命令（Go のネイティブで
  約 50 秒。wasm ではさらにかかる見込み）。初回は最高速で起動し、進み具合
  （スプラッシュ・Today の描画）を表示し、Today に着いたら自動でスナップショットを
  保存する。2 回目以降はそこから数秒で再開する。
- PC のキー入力: 日本語 IME が有効だとキーが変換に取られる。`KeyboardEvent.code`
  で判定し、`isComposing` 中の入力は送らない。画面にフォーカスがある間は IME を
  切るよう案内する（WM5 側の文字入力は SIP か、英数キーの直接入力）。
- 音は対象外（未実装のため）。
- カーネルのデバッグシリアル（UART1）の出力は、開発用のログ欄に出せるようにする
  （起動の様子と停止原因の調査に使う。普段は隠す）。
- エミュレーションが止まったとき（未実装命令・BusError）は、PC・命令語・直前の
  命令履歴を表示し、「直前の自動保存から再開」「スナップショットを書き出す」を出す
  （不具合報告に使えるように）。

### 7.2 Worker とのメッセージ（案）

メイン → Worker:
`importImage(file)`、`boot(imageId, rtc)`（リセットして起動。rtc はローカル時刻の
年月日時分秒）、`resume(snapshot)`、`run`、`pause`、`setSpeed(1|2|max)`、
`input({t, x, y, key})`、`saveSnapshot(slot)`、`listSaves`、`deleteSave`、
`exportSnapshot`、`importSnapshot(file)`、`recordStart`、`recordStop`、
`playScript(text)`（記録の再生。確認用）

Worker → メイン:
`frame(rgba, width, height, seq)`（変化時のみ・transfer）、`status(steps, 仮想時間,
実時間比, 命令/秒, アイドル割合, 一時停止中か, 速度, 記録中か)`、`saved(slot, 命令数)`、
`saves(一覧)`、`recorded(script, 起点スナップショット)`、`uart(bytes)`（ログ欄用）、
`stopped(理由, PC, 命令語, 直前の命令履歴)`、`error(message)`

入力は Worker が次に止まった命令境界で emu の Inject に渡す（serve と同じ規則）。
記録は絶対命令数のスクリプトで、Rust のネイティブ CLI で再生できる（Go 版との
互換は要らない）。

### 7.3 ストレージ

- **OPFS（Origin Private File System）** を基本にする。Worker からは同期アクセス
  ハンドルで大きなファイルを速く読み書きできる（対応ブラウザ・版数は段階3 の前に
  要確認）。
- 保存するもの:
  - イメージ: ユーザーがファイル選択で読み込み、SHA-256 をキーに OPFS に保存
    （再配布できないので、配信側には置かない）。
    - Microsoft の配布物は .msi（中に CAB）で、今は PC 上で抽出してから使っている。
      ブラウザで .msi から直接取り出す機能（CAB・圧縮形式の実装が要る）は
      **判断が必要**（段階3 では抽出済みの .bin を読む前提にする）。
  - スナップショット: 手動保存のスロット、自動保存のリング（例: 最新 3 世代）。
  - 記録: スクリプトと起点スナップショットの組。
- **原子的な保存**: 一時ファイルに書き終えてから置き換える（OPFS の move が
  使えない環境では、2 スロットを交互に使い、ヘッダの検証が通る新しい方を採る）。
  読み込み時は形式の検証（長さ・チェックサム。§4.3）で壊れたものを除外し、
  1 つ前の世代に戻る。
- **容量と消去への備え**:
  - `navigator.storage.persist()` で永続化を要求し、`estimate()` で残量を表示する。
  - **要確認**: iOS/iPadOS の Safari は、しばらく使われていないサイトのデータを
    消すことがある（ホーム画面に追加した Web アプリは扱いが違うとされる）。
    版ごとの正確な規則を段階3 の前に一次情報（WebKit の公式発表）で確認する。
  - 対策として、スナップショットとイメージの **書き出し（ダウンロード・共有シート）
    と読み込み** を必ず用意し、UI で定期的な書き出しを勧める。
- **スナップショットの軽量化**（自動保存の頻度を上げるため。段階3 で判断）:
  - 案 A: 差分スナップショット（前回の基準から変わった RAM ページだけ）。
    RAM への書き込みでページに印を付ける必要があり、ホットパスへの影響を計測して
    決める（書き込み保護方式を流用できる可能性がある）。
  - 案 B: 圧縮レベルと形式の見直し（形式の版数を上げる）。
  - いずれも「展開後の状態」が同じになることを一致確認の対象にする。
- **スナップショットにはイメージの中身が入る**（RAM に展開済みの ROM）。書き出した
  スナップショットも Microsoft の再配布物を含むので、公開の場で共有しないよう
  UI（書き出し時）と README に書く。不具合報告にはスクリプト（入力の記録）と
  イメージ ID を添える形を勧める。

### 7.4 kill・ライフサイクル

- **自動保存**:
  - 定期的（例: 壁時計で数十秒ごと、または操作が止まったとき）
  - `visibilitychange`（hidden）、`pagehide`、Chrome の `freeze` で保存する
  - iOS はイベントなしで落とすことがあるので、**定期保存だけが確実な手段** と考える
- 非表示中はエミュレーションを止める（ブラウザがタイマーを絞るため。決定論的なので、
  止めても再開後の結果は変わらない）。
- 起動時に最新の有効な自動保存を見つけ、「続きから再開」を出す。
- **複数タブ**: 同じサイトを 2 つのタブで開くと、同じ保存領域に自動保存が衝突する。
  Web Locks API で「エミュレーションを動かすのは 1 タブだけ」にし、2 つ目のタブには
  その旨を表示する。
- **保存の失敗**（容量超過など）: 失敗を必ず表示し、古い自動保存の世代を消して
  再試行するか、書き出しを促す。失敗した書きかけのファイルは残さない（§7.3 の
  原子的な保存）。
- **再開後のゲストの時計**: スナップショットから再開すると、ゲストの RTC は保存時点の
  続きで、実際の日時からずれる（決定論のため意図どおり）。ユーザー向けには「時計を
  今に合わせる」操作が欲しくなるが、決定論を保つには **記録される入力イベント**
  （スクリプトの新しいコマンド）として扱う必要がある。段階1 の完了後なら Rust 版だけに
  入れてよい（§1 の凍結の範囲）。**判断が必要**（段階3 の前に扱いを決める。当面は
  ずれたままにする案もある）。
- **記録中の kill**: 記録の途中で落ちて自動保存から再開すると、記録は途切れる。
  記録の途中経過（起点スナップショットとそこまでの入力）も自動保存に含めて、
  再開後に記録を続けられるようにするかは **判断が必要**（段階3）。
- メモリの使いすぎで落とされないよう、§6.2 の予算を守る。
- wasm の panic（trap。§6.2）や Worker の異常終了は検出し（Worker 内での
  `RuntimeError` の捕捉と、メイン側での Worker の error イベント）、止まった理由を
  表示して、直前の自動保存からの再開を出す。panic の直後に自動保存をしない
  （壊れた状態を保存しないため）。

### 7.5 配信

- 静的サイト（HTML/JS/wasm）。PWA（manifest と Service Worker）でオフライン起動と
  ホーム画面への追加に対応する。
- アプリの更新（Service Worker の更新）で、保存済みのスナップショットが読めなく
  ならないようにする。形式を変えるときは版数を上げて旧版の読み込みを残す（§4.3）。
  更新の適用は、エミュレーションを止めて自動保存した後に行う。
- 配信先の候補（GitHub Pages 等）はユーザーと決める。SharedArrayBuffer を使わない
  限り、特別なヘッダは要らない。
- イメージは配信しない（ユーザーが自分で用意）。README に入手手順を書く
  （今の README の手順と同じ）。
- イメージ・スナップショット・入力はすべて端末内で処理し、外部に送らない
  （サイトはネットワーク通信をしない。解析・広告のスクリプトも入れない）。
- **Content-Security-Policy**: 配信側で CSP を設定する場合、wasm の実行には
  `wasm-unsafe-eval`（古いブラウザでは `unsafe-eval`）が要る。JIT-to-wasm（段階5）で
  実行時に wasm を生成・instantiate するのも同じ許可に含まれる。配信先を決めるときに
  確認する。
- iOS/iPadOS の **ロックダウンモード** では WebAssembly が無効になり動かない。
  wasm が使えないことを検出したら、その旨を表示する。
- 使った依存（Rust のクレート）のライセンス表記をサイトに含める。

### 段階1: コアの移植（インタプリタ、ネイティブで Go と完全一致）

- 移植の順序（それぞれテストを移しながら）:
  0. 所有権の設計（§3.3）の案を決める。保存対象の状態と派生情報の分け方
     （§4.3・§5.4 の CheckFields 相当）もここで決める
  1. loader
  2. bus
  3. mmu（TLB を含む）
  4. cpu/arm（まず素直な 1 命令ずつの実行）
  5. s3c2410 の各デバイス
  6. smdk2410（構成・入力）
  7. script・emu
  8. snapshot（Rust の形式。§4.3）
- **最初の結合確認**: loader〜smdk2410 が揃った時点で、リセットからの trace-hash を
  Go と突き合わせる（boot-1200M）。ブートの序盤は CPU と MMU の有効化が中心で、
  デバイスは後半に順に効いてくるので、食い違いを前から順に潰していける。その後
  boot-today、script・emu を入れて today-calendar・taps-5 に進む。
  snapshot は一致を確かめた後に入れ、保存 → 読み込み → 続きの実行が通し実行と
  一致することを確かめる（§5.4）。
- CLI（run・info・トレース・履歴・監視・sample・fb-out・snap-save/load・script・stats・
  snapdump・trace-hash・§5.1 の結果の出力）。開発に必要なので早めに作る。
  フラグ名と出力の書式は Rust で決めてよい（Go の CLI に揃える必要はない）。
  Go の CLI にある調査用の機能（-touch-raw・-nb0-base・-no-idle-skip など）は、
  要るものを選んで移す。Go の serve（HTTP フロントエンド）は移さない（ブラウザ版が
  置き換える）。
- まず **高速化なし** で一致させる。次に Go の高速化を 1 つずつ移し、そのたびに
  一致を確認する（高速化は状態を変えないので、一致したまま速くなるはず）。
- 完了条件: 全基準シナリオで Go と完全一致する（§5.1 の値。途中の点も含む）。
  Rust のスナップショットからの再開が通し実行と一致する。移植したユニットテストが
  通る。ネイティブの速度を記録する。期待値を Rust で作り直す手順を用意し、
  以降の基準を Rust 版に切り替える（§5.2）。
- **結果（2026-09-28）**:
  - 全 6 基準シナリオ（合成 2・boot-1200M・boot-today・today-calendar・taps-5）で、
    途中の点を含め Go の期待値と完全一致（CPU 状態のダンプ・RAM・UART1・画面・停止の
    種類）。最初の「高速化なし」の段階で一致し、その後 Go の高速化を 1 つずつ移して
    一致を保った（デコードキャッシュ → アイドルスキップ → 特化・LDM/STM）。
  - Go と Rust の CPU の差分テスト（`tools/armvec.sh`。同じ乱数列から作った
    ランダムな状態・命令語 20 万件の 1 命令実行）もデバッグビルドで一致。
  - 移植で見つけた違い: MMIO の読み書きのアクセス幅の切り詰め（Go は型で暗黙に
    行っていた）を bus に入れた。Go の動作として、ARM の cond=1111 は NOP になる
    ことを確認（Rust も合わせた。CLAUDE.md）。Go 版の不具合は見つからなかった。
  - スナップショット（§4.3 の Rust 形式）: 保存→読み込み→続きの実行が通し実行と
    一致（合成で全状態を比較）。実イメージでも Rust で Today（36 億命令）を保存し、
    再開して taps-5 を実行した結果が Go の期待値と一致した。
  - 速度（ネイティブ、この開発機、release）: リセットから 4 億命令は Go 78.7M /
    Rust 82.4M 命令/秒（`tools/bench/compare.sh`、3 回交互の最良値）。boot-today
    （36 億命令）Go 約 47 秒 / Rust 44 秒、taps-5 のリセットからの通しは Go 約 50 秒 /
    Rust 47 秒。Today のスナップショットからの taps-5 の再生は Go 2.4 秒 / Rust 2.5 秒
    （Rust は無圧縮 134MB の読み込みと CRC 検査に約 0.5 秒）。§6.1 の見込み
    （1.5〜3 倍）には届いていない。同じ設計のままでは言語の差は小さく、速くするには
    段階4（IR・スーパー命令）が要る。
  - 期待値を Rust で作り直す手順: `GOLDEN_IMPL=rust tools/golden/regen.sh`。
    基準を Rust 版に切り替えるかと Go 版の退役時期はユーザーと決める（§12-7）。
  - 未移植（必要になったら）: Go の CLI の -touch-raw・-nb0-base・-cpuprofile、
    tmp/tools 相当のサブコマンド（segspeed・ihist・genrate。§6.3）。

### 段階2: wasm で動かして測る

- core を wasm にビルドし、Node と各ブラウザで基準シナリオを走らせて、ネイティブの
  Rust との一致と速度を確認する（最小の Worker と、計測用のページ）。
- デコードキャッシュのメモリ使用量を測り、予算を決める（§6.2）。
- スナップショットの保存・読み込みにかかる時間（128MB の圧縮・展開と OPFS への
  書き込み）を測り、自動保存の頻度と差分スナップショットの要否の材料にする。
- 完了条件: wasm でも完全一致する。Chrome/Firefox/Safari（Mac）と iOS Safari の
  速度を記録する。
- **判断が必要**: wasm の速度を見て、段階3 と段階4 のどちらを先にするか。

### 段階3: ブラウザ版の最小製品（MVP）

- Worker＋UI（§7.1〜7.2）。イメージの読み込みと OPFS への保存。スナップショットの
  保存・読み込み・書き出し・読み込み。自動保存と再開（§7.3〜7.4）。記録と書き出し。
  PWA 化。
- 完了条件: PC の 3 ブラウザと iOS Safari で次が確認できる。
  - 起動（またはスナップショットから再開）→ 操作 → 記録 → 書き出したスクリプトを
    ネイティブ CLI で再生して同じ画面
  - タブを閉じる・リロード・強制終了（iOS はアプリスイッチャーで終了）から、
    自動保存で再開できる
- **判断が必要**: 配信先（CSP を含む）、対応ブラウザの最低版数、タッチ UI の配置、
  差分スナップショットの要否、再開後のゲストの時計の扱い、記録中の kill の扱い、
  UI の言語。

### 段階4: インタプリタの高速化 II（IR とスーパー命令）

- ARM の基本ブロックを小さな中間表現（IR）に変換し、IR を直接実行する
  インタプリタ（スーパー命令・フラグ計算の遅延など）にする。IR は段階5・将来の
  ネイティブ JIT と共通にする。
- 決定論性の要件: ブロックの途中でも正確な命令数で止まれること（期限・LimitRun・
  MMIO・割り込み・アボート）。各 IR 命令に元の命令数の対応を持たせる。
- 完了条件: 基準（Rust のネイティブのインタプリタ）と完全一致を保ったまま、
  重い区間の速度が段階1 を上回る（目標値は
  段階2 の計測を見て決める）。

### 段階5: JIT-to-wasm

- IR → wasm 関数を生成し、同じ線形メモリ（CPU の状態・ゲスト RAM・TLB）を
  import した小さなモジュールとして動的に instantiate する。
- 段階的なコンパイル: まずインタプリタで実行し、よく実行されるブロックだけ
  コンパイルする。複数のブロックを 1 モジュールにまとめ、instantiate の回数を減らす。
- 正確さの要件:
  - 命令数を正確に数え、期限で止まる
  - MMIO のアクセスはコアの関数を呼ぶ（呼んだ後に割り込み線・期限・LimitRun を確認する）
  - TLB の fast path は生成コードの中に埋め込み、ミスはコアに戻す
  - コードの書き換えは書き込み保護の通知で、生成済みのブロックを捨てる
  - アボートは正確な PC で例外にする
- 検証: JIT とインタプリタで基準シナリオが完全一致すること。ランダムな命令列の
  差分テスト。trace-hash の突き合わせ。
- 完了条件: 完全一致を保ったまま、重い区間がインタプリタより大きく速い。
  目標は重い区間で実時間（135.2M 命令/秒）以上。Safari（iOS 含む）で動く。

### 段階6（範囲外・将来）: ネイティブ

- iOS（App Store 版はインタプリタ、StikDebug 等の環境ではネイティブ JIT）、
  Android、PC のフロントエンドとネイティブ JIT。コアはそのまま使い、
  C ABI（または uniffi 等）で包む。
- iOS では「WKWebView の殻＋wasm コア（JIT-to-wasm）」も比較する価値がある。

### Go 版の扱い

- 段階1 の間は、動作の正解の基準として維持する（動作は凍結、不具合修正だけ両方に
  入れる）。
- 段階1 の完了後は基準を Rust 版に切り替え、Go 版は凍結する（直さない・比較にも
  使わない）。Go 版をリポジトリから消す時期（段階1 の完了直後か、段階3 の後か）は
  ユーザーと決める。消す前に CLAUDE.md の「確認済みの事実」と設計の理由コメントが
  Rust 側に移っていることを確かめる。

## 10. 将来の拡張を妨げないための約束

- コアはプラットフォーム非依存（std のみ、ファイル・時計・スレッドに触れない）。
  ネイティブのフロントエンドは C ABI で包めるように、公開 API の型を単純に保つ
  （バイト列・整数・文字列・コールバック）。
- 実行方式（§3.2）はコアの内部で差し替えられる。machine・スナップショット・入力・
  記録は、実行方式に依存しない。
- machine の差し替え（将来の PXA27x）を妨げない（S3C2410 固有の知識を広げない）。
- ARMv5TE（PXA27x）の拡張命令は未実装のまま、デコーダの拡張点を残す。

## 11. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| ゲストの動作に現れる実装の細部の見落とし（§4.1） | 一致しない・原因が分かりにくい | trace-hash の二分探索と -trace・-watch の突き合わせ。細部の一覧を育てる |
| 比較がゲストから見える値だけなので、デバイスの内部状態の食い違いが遅れて現れる | 原因の特定に時間がかかる | 割り込みの時刻の違いとして CPU 状態に現れるので、そこから -watch でデバイスへのアクセスを比べる。必要なら比較の値にデバイスのレジスタ（INTC の SRCPND 等）を足す |
| Rust のシフト・オーバーフローの意味の違い | panic や計算の違い | wrapping 演算とシフト量の場合分けを規則化。ランダム差分テスト |
| wasm の速度が想定より低い | 体感が悪い | 段階2 で早めに計測し、段階4・5 の優先度を決める |
| iOS Safari のメモリ上限・ストレージの消去 | タブが落ちる・データ消失 | メモリ予算、定期的な自動保存、書き出しの導線 |
| JIT の正確さ（命令数・例外・書き換え） | 非決定性 | インタプリタとの差分検証を常時の条件にする。まず小さな範囲から |
| 移行中の Go 版と Rust 版の二重保守 | 作業量 | 段階1 の間だけ動作を凍結し、完了後は Go 版を凍結・退役する |
| 依存の追加・更新 | 保守・ライセンス | 追加のたびに承認。コアの依存は最小に |
