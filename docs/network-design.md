# ネットワーク（NE2000 の PC カード＋中継サーバー）の設計

## 決定事項（2026-09-30 ユーザー決定）

- **ゲスト側**: 82365SL 互換のコントローラ（ストレージカードで実装済み）に挿す NE2000 互換の
  PC カード（DP8390 相当の NIC）。
- **ホスト側は案 B**: ARP・DHCP・DNS・TCP の終端（ユーザー空間の NAT）を std のみの自作
  クレート `net`（cerulean-net）に置き、ブラウザ（wasm）と CLI で共有する。外へは TCP の
  バイト列だけを出す。
  - 案 A（イーサネットのフレームをそのまま中継し、サーバー側で TAP か NAT）は、サーバーに
    root か結局 TCP のスタックが要り重くなるので選ばなかった。
- **TCP のスタックは自作**（smoltcp 等の依存は使わない）。相手は WM5 だけで仮想の線は失われ
  ないので、必要な分（順番どおりの受信・go-back-N の再送・ウィンドウ）だけにする。
- **中継サーバーは Rust の CLI のサブコマンド**（`cerulean relay`）。WebSocket（RFC 6455）・
  SHA-1・Base64 も自前で、依存を増やさない。
- **安全対策はトークン認証**（接続の最初にトークンを確かめ、違えば切る）。待ち受けの既定は
  127.0.0.1（`--listen` で変える）。
- UI: メニューの「ネットワーク（中継サーバー経由）」のトグル（既定はオフ）と中継サーバーの
  URL・トークン。オン・オフはイーサネットカードの挿入・抜去としてゲストに見せ、記録する。
  オンにしたときだけ、ユーザーが指定した中継サーバーと通信する。

## 観察結果（2026-09-30、PPC_JPN.bin）

調べ方: `--nic` でカードを挿したまま起動し、`--watch 0x10000000-0x17FFFFFF` と
`tools/re/pcicwatch.py`、ne2000.dll（JPN 版は VA 0x013D0000〜）の `--trace`。

### 検出と構成

- 約 5.05 億命令目に pcc_serv が CIS を読み、PCMCIA の検出の表（serial → atadisk → NE2000）の
  NE2000 が名乗り出て ne2000.dll が読み込まれる（CISTPL_FUNCID = 06h の CIS で）。
  TODO: DetectNE2000 がどのタプルを見ているかは未確認。
- 構成: I/O 窓 0x300〜0x31F（CIS の範囲どおり）、COR = 41h（構成 1・レベル割り込み）、
  CCSR に 20h（IOis8 = 8 ビットのホスト）。Card IRQ Select はストレージカードと同じ 3
  （→ EINT8）。
- 初期化の後、ドライバは Sleep(2000) を挟む（約 2.7 億命令）。

### DP8390 の使い方（ne2000.dll）

- **8 ビットのカードとして使う**: DCR = 48h（WTS = 0・LS = 1・FT = 8 バイト）。I/O は
  すべて 8 ビット。
- **局アドレス**: リモート DMA でアドレス 0000h から 12 バイトを読み、偶数番目のバイトを局
  アドレスに使う（奇数番目は読み捨てる）。レジストリの局アドレスが全 0 のときだけ PROM を使う。
  → PROM は各バイトを 2 回ずつ並べる。
- **バッファ**: 送信 4000h〜4BFFh（TPSR = 40h・45h 等）、受信リング PSTART = 4Ch・PSTOP = 80h、
  BNRY = 4Ch・CURR = 4Dh（BNRY は「次に読むページ − 1」の慣習）。→ RAM は 4000h〜7FFFh の
  16KB とした（NE2000 の慣習と一致）。
- **受信バイト数**: ドライバは「受信バイト数 − 4」をフレームの長さ（FCS なし）として 60〜1514 を
  確かめ、ヘッダの 4 バイトの後から「長さ＋14」バイトを読む（14 バイト余分に読むのはドライバの
  癖）。→ 受信バイト数は FCS を含みヘッダを含まない（DS 4.0 の「SFD の後のバイトを数える」とも
  合う）。
- IMR = 1Bh（PRX・PTX・RXE・OVW）、RCR = 0Ch（ブロードキャスト・マルチキャスト）。
  マルチキャストのフィルタに IPv6 の全ノード等のビットを立てる。

### ゲストの動き（ホットプラグ）

- 挿すと DHCP（DISCOVER → REQUEST）、ARP（重複の確認）、IPv6 のルーター要請、`isatap` の
  名前解決をする。`isatap`（点のない名前）に仮のアドレスを返すと ISATAP のトンネル
  （IPv4 に包んだ IPv6）を送ってくるので、点のない名前は NXDOMAIN にした。
- **IE で開くには、WM5 の「設定 → 接続 → ネットワークカード」で「ネットワークカードの接続先」を
  「インターネット設定」にする必要がある**（既定の「社内ネットワーク設定」のままだと
  「接続できません」）。スナップショットに入る設定なので一度でよい。
- 割り込みの処理（IST）は、IE 等が忙しいと送信完了の割り込みから 2〜3 百万命令（約 20ms）
  遅れて動くことがある（EINT8 は OAL がマスクしたまま）。ゲストのスケジューリングによるもので、
  受信はその間リングに溜まる。

## 実装（2026-09-30）

- **コア**（`core/src/pccard/ne2000.rs`）: CIS・構成レジスタ（COR・CCSR）・DP8390 の
  ページ 0〜2 のレジスタ・リモート DMA（Remote Read/Write・Send Packet）・送信（TXP で即座に
  完了してホストへの列に積む）・受信（アドレスのフィルタ・受信リング・BNRY での中断と OVW）・
  リセットポート。仮想時間を持たない（送受信は瞬時）。
  - ソケットのカードは `pccard::Slot`（CF か NIC）。スナップショットは machine の版数 3 で
    `ne2000` チャンクを足した（版数 1・2 も読む）。
  - Machine の API: `insert_nic(mac)`・`eject_any_card()`・`net_take_tx()`・`net_receive(frame)`。
  - 入力（script・emu）: `nic insert [MAC]`・`nic eject`・`net rx <16 進>`。ネットワークから
    来たフレームはすべて `net rx` として命令数つきで記録する（再生はネットワークなしで同じ状態）。
- **スタック**（`net`、cerulean-net）: sans-IO（ソケット・時計に触れない）。
  - 仮想の LAN 10.0.2.0/24: ゲートウェイ 10.0.2.2（DHCP サーバーを兼ねる）・DNS 10.0.2.3・
    ゲスト 10.0.2.15。ゲートウェイの MAC は 02:43:52:4C:4E:FE。
  - DNS は名前ごとに仮のアドレス（198.18.0.0/15）をすぐに返し、そのアドレスへの接続は名前で
    外に作る（外の名前解決は接続する側）。存在しない名前は接続の失敗（RST）として見える。
    AAAA 等は回答なし、点のない名前は NXDOMAIN。
  - TCP: ゲストの SYN で外への接続を依頼し、結果を待って SYN-ACK か RST。順番どおりの
    データだけ受け取る。ゲストへの送信は MSS ごと・確認待ちは 8KB まで（NE2000 の受信リング
    約 13KB を溢れさせない）・go-back-N の再送（500ms〜8s）。
- **CLI**: `--nic`・`--net`（OS のソケットで直接。実時間に合わせて進める）・
  `--net-record F`（受け取ったフレームのスクリプト）・`--net-pcap F`（送受信の pcap。時刻は
  仮想時間）・`--net-verbose`。`--script` は複数指定できる（再生は元のスクリプトと記録を並べる）。
- **中継サーバー**: `cerulean relay [--listen A] [--token T] [--allow-private]`、またはアプリの
  配信と同じポートの `/relay`（`cerulean serve --with-relay`。cli/src/serve.rs）。約束は
  relay.rs の先頭のコメント。既定では私的アドレス（LAN・localhost・CGN 等）への接続を断る
  （2026-09-30 追加。家の LAN への踏み台にならないように）。WebSocket 1 本に接続を多重化し、接続ごとに CREDIT（ブラウザが受け
  取れる量）の範囲で読む。
- **ブラウザ版**: メニューの「ネットワーク（中継サーバー経由）」。Worker が WebSocket を持ち、
  run の合間（10ms ごと）に wasm の `netStep` でスタックを進める。中継が切れたら 5 秒ごとに
  つなぎ直し、生きていた接続はゲストにリセットとして見せる。ソケットは 1 つなので、オンの間の
  ストレージカードは Device Emulator のフォルダ共有の方式で挿す（docs/folder-share-design.md）。
- 確認: `tools/browser/app-net.mjs`（中継を起動 → メニューでオン → IE で example.com →
  記録を CLI で再生してハッシュが一致）。コアの単体テスト（PROM・送信・受信リングの折り返しと
  溢れ・スナップショット）、スタックの単体テスト（DHCP・ARP・DNS・TCP の往復・再送・拒否）。
- 基準（`testdata/golden/expected`）は変わらない（カードを挿さない既定の構成ではゲストから
  見える動作が同じ。`tools/golden/verify.sh` で全シナリオ一致）。

## HTTPS（2026-09-30。方式・依存はユーザー承認）

WM5 の IE Mobile は SSL 2.0 互換の ClientHello で TLS 1.0 を求め、RC4_128_MD5・RC4_128_SHA・
3DES_EDE_CBC_SHA と輸出用の弱い暗号だけを出す（AES・拡張・SNI なし。観察）ので、今のサイトとは
直接つながらない。警告なしに使えるよう、ゲストの TLS をエミュレータの外側で終端し、外へは今の
TLS でつなぎ直す:

- **ゲスト側（`net`。std のみ・自作）**: `bigint.rs`（多倍長整数・RSA・Miller-Rabin）、
  `crypto.rs`（MD5・SHA-1・HMAC・RC4・乱数の生成器）、`x509.rs`（DER・自前の CA・名前ごとの
  サーバー証明書。署名は SHA-1、有効期間 2000〜2049 年でゲストの時計に依らない）、`tls.rs`
  （TLS 1.0 のサーバー。RSA の鍵交換・RC4_128_SHA）。443 番への接続は、仮のアドレスから分かる
  名前の証明書をその場で作って受ける（サーバー証明書の鍵は RSA 1024 を 1 つ作って共有）。
  一次資料: RFC 2246・8017・5280・1321・3174・2104・6229。
- **CA の配布**: ゲートウェイの 80 番（`http://10.0.2.2/`）をスタック自身が返す。IE で開いて
  `cerulean-ca.cer` をタップ → 「ダウンロード後にファイルを開く」で「はい」→「CErulean Local CA が
  発行した証明書…をインストールします」で「はい」。一度入れればスナップショットに残る。
  ページには確認用の `https://example.com/` へのリンクもある。
- **外側（CLI のみ。依存 rustls＋ring・webpki-roots）**: `cli/src/upstream.rs` が TCP か TLS
  （Mozilla のルートで名前を確かめる）でつなぐ。中継の約束は版 2（CONNECT にフラグ u8、bit0 = TLS）。
  確かめに失敗した接続はゲストにはリセットとして見える。
- CA の鍵: CLI は `run --net-ca F`（なければ作り、`F.cer` に証明書）。ブラウザ版は OPFS の
  `net/ca.bin`（初めてオンにしたときに wasm で作る。メニューから証明書を書き出せる）。鍵は端末の外に
  出ない。
- 観察・確認: github.com（http → https のリダイレクト）・https://example.com/ が鍵のマーク付きで
  警告なしに表示される。`tools/browser/app-net.mjs` が CA の導入から https の表示、記録の再生まで通す。
- 注意: ゲストと中継の間は古い暗号（RC4）だが、その区間はエミュレータの中（ブラウザ・CLI の中）
  だけ。中継サーバーとブラウザの間は WebSocket（公開するなら wss://）で、その中は平文の HTTP に
  なる（中継サーバーは中身を見られる）。
